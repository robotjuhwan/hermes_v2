# UI

The TradeCraft UI is a static, operator-facing control room for HERMES/쥬. It is not a marketing surface: it exposes live/paper trading state, block ledgers, live authority, research context, memory, LLM usage, settings, auth state, and operational errors for an active KIS and Binance block-trading system.

## Files

- `src/tradecraft/web/static/index.html`
- `src/tradecraft/web/static/app.js`
- `src/tradecraft/web/static/style.css`

## Design Identity

- AI research-room dark theme.
- Financial dashboard density.
- Active trading operations visibility.
- Error/stale/auth states visible.
- Korean-first operating labels with trading terms kept concrete: 블록, 실주문, 바이낸스, 리포트, 메모리, 운영 설정.
- Main navigation is compact and app-like, with the dashboard and helper/trading tabs sharing one static frontend.

## Binance Backtest Lab UI

The crypto research page includes a Binance backtest/optimization lab fed by
`/api/binance/patterns/context`. The panel must show:

- optimized strategy set count, qualified scorecard count, raw scorecard count,
  pattern count, and latest promotion time;
- promoted optimized sets with symbol, pattern key, side, stop percentage,
  target percentage, holding bars, objective score, win rate, expectancy,
  profit factor, trade count, sample window, and promotion time;
- raw scorecards with pass/fail entry-quality status;
- a visible note that optimized sets are price-geometry priors for Jue and are
  not standalone order instructions.

The lab belongs on the `crypto_research` top-level helper page rather than the
Binance block board. The Binance block board remains focused on active blocks,
orders, account state, live authority, and manager/executor controls. The
Binance block board may show a compact "backtest live confluence" panel that
summarizes whether the latest optimized sets agree with quant direction,
spread/book freshness, funding context, and live authority; it must not embed
the full research lab tables there.

## State Rules

- Preserve active page/tab through localStorage/hash.
- `app.js` stores the active UI state under a centralized `state` object, including `activePage`, `activeHelperTab`, `activeVenueId`, auth token state, KIS block state, Binance block state, live authority state, memory, reports, LLM usage, and settings state.
- Active block panels should refresh without forcing full page reload.
- Compact refresh must not overwrite richer account/risk state with empty payloads. `mergeBinanceStatus` specifically keeps prior account, risk, performance, config, blocks, orders, events, and manager runs when the compact Binance endpoint omits them.
- Auth token should live in session storage only. `readAdminToken` and `writeAdminToken` use `sessionStorage`, while page/tab/theme state may use `localStorage`.
- Protected API calls must attach `Authorization: Bearer <token>` and `X-TradeCraft-Admin-Token` when an admin token is present.
- The UI should continue to render auth-required errors, stale process states, failed API calls, disabled trading modes, and missing/stale live authority instead of hiding them behind empty cards.
- Settings edits must preserve dirty state until saved or reset; danger/high-risk settings require explicit confirmation before PATCHing `/api/settings/values`.

## UI Refactor Risks

- Tabs have grown organically and may need IA consolidation.
- Long research text must be readable without truncation traps.
- KIS and Binance block cards need clear venue/status/PnL separation.
- Closed block history should be available without cluttering open block board.
- Auth convenience must not weaken the session-storage token model or make protected trading endpoints look public.
- Binance compact refresh behavior is easy to regress; account/risk/performance should not disappear during passive auto-refresh.
- Settings UI must stay mapped to `AppSettings`/settings catalog keys, especially real-order toggles and secret-bearing fields.
- KIS and Binance actions should remain visually distinct so an operator cannot confuse KRX account/order actions with crypto spot/futures actions.
- Live authority chips should show venue grade, scorecard count, `max_budget_multiplier`, and whether scale-up is allowed, while making clear that restricted/observe-only authority does not equal a kill switch.
- Error states from reports, RAG, LLM usage, memory, market pulse, quant, patterns, and crypto alpha are part of the active trading cockpit and should remain visible.
